Ship Pipeline

How one eas build becomes a live Google Play release, and how it cycles back through testing. Two setups happen independently — your Expo project, and a Google Cloud service account — and they only meet at eas submit. That meeting point is the part most people can describe vaguely and few can actually explain.

Your build — local Expo project + EAS Build
Google Cloud — the identity bridge (service account)
Google Play — the release surface
artifact / credential flow

Stage by stage

Each card separates what's mechanically happening (engineering) from why it matters to the roadmap (product) — the two things an interviewer is usually really asking for at once.

1

Expo project

app.json · eas.json · src/

Engineering: the React Native + TypeScript codebase. app.json/app.config.ts defines the app's identity — package name, versionName, icon, splash, permissions, and any config plugins that will later inject native code without you hand-editing an /android folder. eas.json defines build profiles (development / preview / production), each with its own env vars and distribution type. Supabase keys live as EAS environment variables, not hardcoded strings.

Product: this is where "what the app is called and what it can access" originates — every permission declared here becomes a policy question Play Console will ask about later.

2

EAS Build (cloud)

eas build --platform android

Engineering: Expo's build servers pull your project, resolve the chosen profile from eas.json, and run expo prebuild — generating a real native Gradle project from your config plugins (this is the step "managed workflow" hides from you day to day). It installs dependencies, bundles your JS with Metro/Hermes into bytecode, compiles the native Kotlin/Java shell around it, and signs the result — with a keystore EAS generates and holds for you, or one you upload yourself. Output is an Android App Bundle (.aab), the format Play has required since 2021; EAS also assigns or increments the build's versionCode.

Product: this is the build you'd watch in the EAS dashboard — logs, pass/fail, a QR code to install the artifact straight onto a test device before it ever touches Google.

3

Google Cloud project

console.cloud.google.com

Engineering: a Google Cloud project is not the Play Console app — it's the IAM container that makes automation possible at all. You enable the Google Play Android Developer API inside it, then go to IAM & Admin → Service Accounts and create one: a non-human, machine identity, exactly the same mechanism any Google API (Firebase, Sheets, Cloud Storage) uses for programmatic access.

Product: this step is invisible to the roadmap but non-optional — there is no path from CI to a Play Store release that skips Google Cloud, because Play's publishing API has no other authentication story.

4

Service account + key

Manage keys → Create new key (JSON)

Engineering: from the service account, you generate a long-lived JSON key and download it once. Separately, in Play Console → Setup → API access, the same Cloud project gets linked to your developer account, which makes the service account inviteable under Users & permissions. There you grant it exactly what it needs — typically "view app information," "edit and delete draft apps," and "release to testing tracks / production" — scoped per app if you want least privilege.

Product: this is a real access-control decision, the same category as giving a contractor Drive access. A service account over-scoped with production-release rights when it only needs internal-testing rights is a governance gap worth asking about, especially once more than one app shares it.

5

EAS Submit

eas submit --platform android

Engineering: EAS Submit loads the service-account JSON key from EAS's own credential store, authenticates as that account, and calls the Play Developer API's Edits resource: edits.insert opens a change, edits.bundles.upload attaches the .aab, edits.tracks.update assigns it to a track, edits.commit publishes it. It is literally the scripted version of a human clicking "Create release" in the Play Console UI.

Product: this is the automation that turns "download the .aab, log in, upload it by hand" into a CI step — the difference between a release being a chore and being a command.

6

Google Play Console

play.google.com/console

Engineering: the release lands as a draft on whichever track you targeted. Play re-derives optimized, device-specific APKs from your single .aab at install time (this is what "Play App Signing" actually does), rather than shipping one universal APK to every device.

Product: the console is also where the non-code side of a release lives — store listing copy, screenshots, the Data safety form declaring what the app collects, and content ratings. A code-perfect build still can't ship if these are stale.

7

Testing tracks → Production

Internal → Closed → Open / Production

Engineering: Internal testing is instant, no review, up to 100 testers by email list. Closed testing is where a new personal developer account must clear 12 testers opted in for 14 continuous days — the count resets if a tester drops out and rejoins. Clearing that gate lets you apply for production access; Google reviews within about a week, and that single review is what unlocks both Open testing and Production together, not Open first.

Product: Production releases aren't all-or-nothing — a staged rollout ships to a percentage of new installs (say 5% → 20% → 50% → 100%) and can be halted if Android vitals show a crash-rate spike, which is the real safety net behind "ship confidently."

A

EAS Update (OTA)

eas update --channel production

Engineering: pushes a new JS bundle to a channel (mapped to a build profile); already-installed binaries poll that channel on launch and swap the bundle in. It only works for JS-only changes — UI, logic, copy, most bug fixes. Anything touching native code — a new native module, a new permission, an SDK bump — still needs a full build-and-submit cycle.

Product: this is the hotfix lever that skips the days-long Play review entirely, which is exactly why store policy limits what can ship this way — an OTA update can't change what the app fundamentally does.

What else Play Console and Google Cloud are doing

Beyond hosting the .aab — the parts that come up when someone asks "what's it actually capable of."

Play App Signing

Google holds the final signing key; your local keystore only signs the upload. That's what lets Google re-generate optimized per-device APKs from one .aab, and recover your signing identity if you ever lose your upload key.

Android vitals

Google's own aggregated crash rate, ANR (App Not Responding) rate, and battery/wakelock stats across every real install — a second, independent telemetry source alongside Sentry, and the trigger for an automatic staged-rollout halt.

Pre-launch report

Google auto-installs your build on a farm of physical devices and crawls it, flagging crashes and accessibility issues before a human tester ever sees the build.

Play Integrity API

Lets a backend verify a request genuinely came from your unmodified app, installed via Play, on a genuine device — the anti-cheat layer relevant to the real-time multiplayer games sharing this pipeline.

Store listing experiments

A/B tests icon, screenshots, and description copy against install conversion rate, run entirely inside the console.

The Play Developer API is bigger than Submit

EAS Submit only calls the Edits resource. The same API surface can pull reviews, financial/earnings reports, and validate in-app purchases server-side — worth knowing the door is already open.

Interview-ready glossary

The pairs people conflate under pressure.

TermWhat it actually means
AAB vs APK.aab is the upload format — a bundle Google slices into per-device APKs at install time. You almost never hand-distribute an .aab; a plain .apk is still used for sideloading and CI test installs.
versionCode vs versionNameversionCode is an internal integer that must strictly increase every submitted build (EAS can auto-increment it remotely); versionName is the human string users see, e.g. "1.4.2."
Upload key vs app signing keyThe upload key (yours, in EAS credentials) proves a build came from you; the app signing key (Google's, under Play App Signing) is what actually ships to devices. Losing the upload key is recoverable; it was never the key that mattered to end users.
prebuild / managed workflowThe "managed" Expo workflow means you never see the native /android folder — expo prebuild regenerates it from app.json + config plugins on every cloud build.
Build vs Submit vs UpdateThree separate EAS commands: Build compiles a native binary, Submit uploads it to a store, Update pushes a JS-only patch to already-installed binaries without either.
Service account vs OAuth userA service account is a machine identity with its own long-lived key — no login screen, no human session, built for CI. An OAuth user identity is you, clicking "Allow."
Track vs releaseA track (Internal/Closed/Open/Production, or a custom track) is a distribution channel; a release is one version sitting on one or more tracks at a given rollout percentage.
One Cloud project, many apps. The Google Cloud project and its service account are set up once per Play Console developer account, not once per app — the same key can be invited into Waypoint, Connect, Resonance, and Chatpata's Play Console listings individually, with permissions scoped per app. Each app still gets its own EAS project, its own eas.json, and its own testing-track clock.
